`@floaty/react` is a client module: its entry is marked `'use client'`, so you can render
`<Floaty>` and `<FloatyAnchor>` from Server Components and pass them children as usual.

```tsx title="app/layout.tsx"
import { Floaty } from '@floaty/react';
import { Player } from './player'; // a Client Component

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        {children}
        <Floaty floatyId="player">
          <Player />
        </Floaty>
      </body>
    </html>
  );
}
```

Put `<Floaty>` in a layout that stays mounted across the routes it should survive; anchors
go in the pages.

Hooks (`useFloaty`, `useFloatyState`, `useFloatyTransition`) and `createFloaty` channels'
hooks need Client Components, like any hook. Call `configureFloaty` from a Client Component
module, not during server rendering, so options don't leak across requests.

## Server rendering

- Nothing floats on the server: the overlay layer is created on the client, so floating
  content first mounts after hydration and is not in the server HTML. This avoids
  hydration mismatches.
- Anchors render as plain `div`s on the server, so the layout space is reserved from the
  first paint.
- Anchors only register in the browser.

## Route changes

Navigating between routes that each render an anchor for the same id is a layout switch:
the content animates from the old page's anchor to the new one. If the new page's anchor
mounts a little later (a `loading.tsx` boundary or data fetching), the
[grace period](/docs/guides/multiple-anchors#anchors-that-arrive-late) bridges the gap.
